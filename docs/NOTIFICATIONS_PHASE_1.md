# Notifications: Phase 1 backend

The notification model is an account-owned durable inbox. Trusted server code calls `createNotification` with a verified owner and event-specific input. The service validates content and compact metadata, checks the account's category preference, then inserts through a unique `{ userId, dedupeKey }` index. A duplicate returns `already_exists`; it never updates the original notification. Notification failures in future quiz, badge, and scheduler producers must be isolated from the authoritative operation, logged with owner/event context, retried or reconciled through a durable producer workflow where needed, and must never cause the source quiz or award to roll back.

`GET /api/notifications` uses owner-scoped keyset pagination on `(createdAt, _id)`, with a 20-item default and 50-item maximum. The other route handlers provide indexed unread counts, owner-scoped read transitions, bulk read, and partial preferences. APIs expose allowlisted DTO fields and private no-store responses. Creation deliberately has no public API route. Security notifications ignore preference state and are always enabled.

The `Notification` collection has three query indexes: owner/newest listing, owner/read-state count, and owner/dedupe uniqueness. `metadata` stores only validated IDs, compact event identifiers, counts, and period keys. Targets are constrained to existing internal route patterns. No TTL index is configured: retention/expiration must be defined per category before a later phase assigns `expiresAt` or adds cleanup. Security and achievement records should remain durable; temporary reminder retention needs an explicit product policy.

Preferences are embedded under `User.settings.notifications`; `dailyStudyTime` is a nullable local `HH:mm` value. Existing records normalize to the documented defaults without migration. The user's existing `settings.studyTimezone` remains the only timezone. Preference patches use dotted paths and preserve unrelated settings. Account deletion removes notifications inside the existing required transaction. Full account data export includes notification history and preferences; clear-history and delete-materials operations retain their established study-only semantics.

## Phase 2 frontend

The authenticated shell wraps its existing navbar bell, dropdown, and route content in a user-keyed notification provider. The provider fetches only the unread count at initialization and on focus/visibility changes; the bell fetches the latest five items only while opened. Account identity is keyed by the authenticated shell, and notification state is kept in memory only. A shared notification row and centralized category presentation are used by both the dropdown and `/notifications`.

The Notification Center requests bounded pages from `GET /api/notifications`, appending with the opaque `(createdAt, _id)` cursor. The supported filters are All, Unread, Reminders, Achievements, and System. The group filters use the validated `group=reminders|achievements|system` query, mapped server-side to the registry types; single-type filters remain supported by the API for future use. Category destinations use only the validated `target` returned by the backend. Read actions use the existing PATCH routes and refresh the shared unread count. The Settings section uses the dedicated preferences API and retains the existing study timezone.

The dropdown is portaled to the document body so it escapes the authenticated shell's clipped scroll region. On narrow screens it becomes a viewport-contained sheet above the mobile navigation. It closes on Escape, outside interaction, route changes, and opening the profile menu. Motion is brief and reduced to opacity for users requesting reduced motion.

## Phase 2 scope and limits

Phase 2 only displays and manages notifications already persisted by trusted server services. There are no notification producers in the client, no generated sample records, and no scheduling or polling. Users may therefore see an empty inbox until later producer phases ship. The navbar refreshes the count at shell initialization and when the page regains focus; live delivery is not provided.

## Phase 3 event producers

`notifyLiveBadgeAward` is called only by the shared badge evaluation boundary after reconciliation reports a newly inserted award and the persisted `UserBadge.source` is `live`. Official badge names come from the badge catalog. Backfill and dry-run reconciliation do not notify. The event key is `badge-unlocked:<badgeId>`.

Quiz milestones are checked only after `finishSession` reports a new completed transition. The producer requires the session's persisted `quiz-completed:<sessionId>` AchievementEvent and counts the user's compact quiz-completion ledger through that event's verified completion time, using the `{ userId, kind, occurredAt }` index. Only exact totals 1, 5, 10, 25, 50, and 100 create a record, with keys `quiz-milestone:<threshold>`. This count-based rollout does not replay old thresholds: when the feature starts after a user has passed a threshold, later completions do not match it.

Successful password changes, reset-grant transactions, and first email-verification transitions schedule mandatory account-security notifications through Next.js `after()`. Password changes use the incremented session version as operation identity; reset uses the consumed grant's database ID; email verification uses a stable one-time transition key. No credentials, grant tokens, or challenge values enter notification metadata or text. Failed/reused operations do not schedule notices.

What's New publishing is an intentional operator CLI, not an API. Run `npm run publish:whats-new -- --id=feature-v1 --title="A new feature" --message="A manually written update."` for a dry-run preview. Add `--apply` only after reviewing the eligible verified-account count. Optional `--target=/dashboard` is validated by the existing target allowlist; `--batch-size=100` accepts 1–500. Publication selects only verified users whose setting is enabled or absent (legacy default), writes in bounded batches with at most eight concurrent recipients, reports outcomes, and can safely resume by rerunning because `whats-new:<announcementId>` is unique per user. No production announcement was published during implementation.

All producers use the existing `createNotification` preference and unique-index policy. Notification write errors are caught and logged with sanitized type/event identity; they never undo the quiz, award, or account change. There is no outbox in this phase, so an infrastructure failure after the authoritative operation can leave the notice missing. Re-running the same producer is safe; future recovery should be a narrowly scoped reconciliation over durable source evidence (live UserBadge records, transitioned quiz sessions/events, security operation evidence, or the manually rerun announcement), not a page-visit side effect. Account changes use Next's post-response callback; delivery still depends on the platform completing that callback. No generic retry worker was added.

Phase 3 activates only Badge Unlocked, Quiz Milestones, Account & Security, and explicitly published What's New. Phase 4 remains responsible for Flashcards Due, Study Streak, Unfinished Quiz, Daily Study Reminder, Weekly Progress, and Study Inactivity notifications, including schedule, timezone, expiration, retention, and retry policy.

## Phase 4 scheduled study reminders

`lib/notifications/reminders.ts` evaluates one verified account at an injected instant and reuses `createNotification()` for all writes. `runReminderBatch()` scans verified accounts (`emailVerifiedAt` is a date) in `_id` order using 50-account pages and a durable cursor/lease in `NotificationScheduleState`. A run can process successive pages for up to 240 seconds, under Vercel's 300-second Hobby function maximum, and checkpoints each completed page. On timeout/restart the current page may repeat; stable notification keys and the unique `{userId, dedupeKey}` index prevent duplicate records. Per-account failures are counted and logged by error class only; the cursor advances so one corrupt account cannot stop the sweep. `hasMore` and `batches` expose partial-sweep progress. A population that cannot be swept within one run is resumed on the next 15-minute occurrence; preferred-time delivery can therefore be later than the nominal time window at larger account volumes.

Eligibility uses the account's existing IANA `settings.studyTimezone`, `studyDayKey()`, and `getStudyDayWindow()`. A configured `HH:mm` daily reminder is eligible from its resolved local instant through 60 minutes later, never before the selected time or on a later local day. The one-hour window accommodates a 15-minute schedule cadence, up to 15 minutes of Hobby dispatch jitter, and a bounded scan delay. Fall-back duplicate times select their first occurrence; a spring-forward missing time moves to the first valid local minute after the requested time. Study streaks use persisted `AchievementEvent` `study-day` evidence, require activity through yesterday and none today, and are evaluated from 7–9 PM local. Completed-week summaries use Monday-to-Monday end-exclusive study-day and quiz-completion events, run Monday 6 AM–noon local with a bounded Tuesday 6 AM–noon catch-up, and skip weeks with no study activity. Inactivity requires prior verified study activity and triggers at three complete local days, with one second tier at ten days; the stable inactivity-event key prevents repeated notices during the same episode. A later study event forms a new episode.

Due Review count starts with current owner-scoped Flashcard rows, joins each card's latest owner/card ReviewRecord sorted by `reviewedAt` and `_id`, and applies the same never-reviewed-or-latest-`nextReviewAt <= now` rule as quiz review selection. The new `review_owner_card_latest_review` index supports that join. Unfinished quizzes require an active, nonempty session, at least 24 hours of inactivity, and future `expiresAt`; one compact record represents the currently oldest eligible idle episode and points to `/review`.

The scheduler enforces a maximum of two motivational reminders per account in a rolling 24-hour period. Study inactivity wins priority and suppresses due and daily reminders after three complete inactive days. Weekly summaries have their own one-per-week limit. Existing preferences are normalized through the Phase 1 defaults. Reminder expiration is: streak through the next local midnight; due and daily study reminders for up to 30 local days; unfinished quiz through the selected session's expiration; inactivity reminders for 30 local days; weekly summaries for 90 local days. No TTL cleanup was added. Expiration only hides records from the existing list and unread-count queries; expired records remain stored and continue to enforce deduplication.

### Phase 4.1 Vercel Hobby schedule integration

`vercel.json` declares one static Vercel Schedule, `notification-reminders`, on `*/15 * * * *` UTC. It targets the private Next.js function built from `app/api/internal/notifications/reminder-schedule/route.ts` (`api/internal/notifications/reminder-schedule`) and uses the `schedule/v1beta` trigger with the official `@vercel/schedules` `handleSchedule()` wrapper. Only Vercel's private dispatch invokes this target; it does not accept a client-supplied user, page size, or timestamp. The existing `GET /api/internal/notifications/reminders` remains a separate protected manual/compatibility route requiring server-only `CRON_SECRET`; it is not registered as a schedule and the schedule handler does not require that secret.

Vercel's current Schedules beta documentation says Hobby schedules have a 15-minute jitter window, may run no more frequently than every 15 minutes, and allow 5,000 scheduled/manual runs per billing period. One 15-minute schedule uses 96 runs/day, or about 2,880–2,976 runs in a 30–31-day month, before any other schedules or manual invocations in the team. The usage allowance is shared at team level. The route's 300-second function cap matches the currently documented Hobby maximum; the runner stops work at 240 seconds, leaving 60 seconds of termination/cleanup margin. These beta limits can change; verify them again before deployment.

The daily reminder window is now one hour after the resolved preferred local time. It never sends before that time or carries a missed reminder into another local day. The window accommodates the documented dispatch jitter and a bounded scan delay, but is not an exact-time delivery guarantee. The scan processes 50-account cursor pages and may resume across schedule occurrences when the account population exceeds a run's 240-second budget. At high account volume, a user's sweep latency can exceed one hour; inspect `batches`, `examined`, `hasMore`, and `durationMs` before promising a tighter delivery window. The stable period dedupe key still prevents repeated daily records.

The schedule handler logs only its name, execution ID, nominal scheduled time, duration, result counts, and completion state. `handleSchedule()` rejects requests that do not contain a valid Vercel schedule dispatch. The cursor is checkpointed after every completed page under a Mongo lease. A later invocation safely resumes; a timed-out page may be repeated and is protected by notification uniqueness. Function/path targets are not automatically retried by Schedules, so inspect failed execution logs and allow subsequent cursor sweeps to recover. There is no additional queue or retry worker.

### Production activation checklist

The repository retains `git.deploymentEnabled: false`; a commit alone will not activate the static schedule. This workspace has no `.vercel` project link, Vercel CLI, or Vercel deployment credentials available, so production registration and a hosted invocation have not been verified. Confirm the team has the Schedules beta enabled before deployment; the SDK requires Node.js 20 or later. The configured project should use the production environment variable `MONGODB_URI` (the exact name read by `lib/mongodb.ts`); the MongoDB URI is never printed here. No `CRON_SECRET` is required for the private function target; the separate compatibility GET endpoint still requires a secret of at least 32 UTF-8 bytes if manually used.

To activate safely, use the existing approved manual production deployment workflow (do not re-enable Git deployment):

1. Confirm the linked Vercel project/team is Abii's intended **Hobby** project, its root is this repository, Schedules beta is enabled, and its Node.js runtime is 20 or later.
2. In Vercel Project Settings → Environment Variables, confirm Production has `MONGODB_URI` and that its value points to the intended production database. Do not paste it into logs or CLI output.
3. Run a production build/deployment using the project's established manual deployment process. The schedule is static and is registered when that deployment becomes current in Production; new static schedules are active there by default and inactive in Preview/custom environments.
4. In the Vercel project **Schedules** page, confirm one `notification-reminders` schedule, `*/15 * * * *`, UTC, target `api/internal/notifications/reminder-schedule`; verify its trigger is private and there is no duplicate legacy Cron entry.
5. Inspect its execution history and sanitized Function logs after a natural run. Confirm outcome `completed` or `partial_batch`, increasing cursor progress, expected database connectivity, and no unexpected account errors. Avoid manually invoking a live run just for validation because it can create real notifications.
6. Check team Schedules run usage and Function invocations/duration. A full 15-minute schedule is about 2,880–2,976 scheduled runs per 30–31 day month, excluding other team schedules and manual invocations.

The daily study preference UI remains truthful until this production activation and hosted execution are verified. After activation, the wording describes delivery as approximate around the saved time, not exact. This remains in-app delivery only; no email, push, websocket, or background queue is used.

Run `npm run test:notification-reminders` for deterministic timezone timing, scheduler authentication, real isolated MongoDB eligibility and cursor behavior, and static schedule configuration coverage. Production schedule registration and hosted invocation must be verified in Vercel separately; local `next build` is not evidence of hosted schedule execution.
